# 后台消息设置设计

## 目标

在现有前端新增“后台消息设置”频道，让用户配置后台推送间隔、最低市值和最低月均成交量。配置由后端持久化到 SQLite，应用重启后继续保留；后台调度器无需重启即可在下一个固定对齐时刻采用最新配置。

## 本次范围

第一版包含：

- 新增“后台消息设置”频道和独立设置页面；
- 每次进入设置页时从后端读取数据库中的最新配置；
- 点击“保存设置”后统一校验并持久化；
- 推送间隔支持 10 至 120 分钟，步长 10 分钟，默认 60 分钟；
- 后台最低市值和最低月均成交量使用与首页相同的范围、步长、默认值和显示格式；
- 设置页与首页使用独立组件实例和独立状态，两者的当前值不联动；
- 调度器按中国时间固定钟点对齐，并动态采用数据库配置；
- 美股和港股在同一轮扫描中使用同一份配置快照。

本次不包含：

- 在页面中管理 `ENABLE_MESSAGE_PUSH`；
- 在页面中管理 PushPlus Token 或其他密钥；
- 配置历史、版本回滚或审计页面；
- 按市场分别配置筛选条件；
- 修改现有技术指标公式和建仓判断。

## 配置模型

新增全局单例配置表 `message_push_settings`。第一版只允许一条有效记录，使用固定主键保证所有调用方读取同一份配置。

字段：

- `id`：固定单例主键；
- `interval_minutes`：推送间隔分钟数；
- `min_market_cap`：最低市值；
- `min_avg_volume`：最低月均成交量；
- `updated_at`：最后更新时间。

默认值：

```text
interval_minutes = 60
min_market_cap = 200000000000
min_avg_volume = 10000000
```

当数据库中没有配置记录时，后端在读取配置时创建默认记录并返回。数据库是唯一配置来源；前端默认值不能替代读取失败的数据库配置。

## 共享筛选规格

首页和后台设置页保持以下规格一致：

### 最低市值

- 最小值：500 亿；
- 最大值：2 万亿；
- 步长：500 亿；
- 默认值：2000 亿；
- 显示格式与首页现有 `formatLargeMoney` 一致。

### 最低月均成交量

- 最小值：100 万；
- 最大值：1 亿；
- 步长：100 万；
- 默认值：1000 万；
- 显示格式与首页现有 `formatVolume` 一致。

前端将这些规格和格式化规则提取为共享定义，避免两个页面后续发生漂移。首页和设置页分别渲染组件并分别管理状态：修改首页筛选不会修改后台配置，修改设置页草稿也不会影响首页。

## 前端频道与页面

现有频道增加第三项：

```text
后台消息设置
```

进入该频道后：

- 不请求日线或分时筛选接口；
- 不展示市场选择、股票表格或分页；
- 展示独立设置卡片；
- 顶部状态文案反映配置加载或保存状态。

设置卡片包含：

1. 推送间隔滑块：
   - 最小 10 分钟；
   - 最大 120 分钟；
   - 步长 10 分钟；
   - 显示为“每 N 分钟”。
2. 最低市值滑块。
3. 最低月均成交量滑块。
4. “保存设置”按钮。

## 页面数据流

每次切换到“后台消息设置”频道时都执行一次读取请求，不复用上一次进入页面时的配置：

1. 页面进入加载状态；
2. 禁用设置控件和保存按钮；
3. 调用读取配置接口；
4. 成功后使用响应值同时初始化“已保存值”和“草稿值”；
5. 失败时显示“配置读取失败”和重试按钮，不用前端默认值伪装成数据库配置。

编辑与保存行为：

- 草稿值与已保存值相同时，保存按钮不可用；
- 任一草稿值发生变化后，保存按钮可用；
- 保存期间禁用所有控件，防止重复提交或继续修改；
- 保存成功后，使用后端响应值同时更新已保存值和草稿值；
- 成功提示为“设置已保存，将从下一个固定钟点生效”；
- 保存失败时保留用户当前草稿并显示错误；
- 带有未保存修改时离开设置页，修改直接丢弃；
- 再次进入设置页时重新读取数据库配置并还原页面。

## API

新增两个接口：

```http
GET /api/message-push-settings
PUT /api/message-push-settings
```

读取响应数据：

```json
{
  "interval_minutes": 60,
  "min_market_cap": 200000000000,
  "min_avg_volume": 10000000,
  "updated_at": "2026-07-31T10:00:00+08:00"
}
```

保存请求使用完整配置，不接受局部更新：

```json
{
  "interval_minutes": 30,
  "min_market_cap": 250000000000,
  "min_avg_volume": 12000000
}
```

后端必须校验：

- `interval_minutes` 在 10 至 120 之间，且能被 10 整除；
- `min_market_cap` 在 500 亿至 2 万亿之间，且符合 500 亿步长；
- `min_avg_volume` 在 100 万至 1 亿之间，且符合 100 万步长。

保存成功后返回最终落库配置及更新时间。接口继续使用项目现有统一响应结构和请求 ID 错误处理，不向客户端暴露数据库内部异常。

## 固定钟点调度

所有对齐计算使用：

```python
ZoneInfo("Asia/Shanghai")
```

每天以中国时间 `00:00` 为对齐基准，从该基准按配置的分钟数连续划分执行点。这样 20、40、50、70、80、90、100、110 分钟等所有合法间隔都有唯一、稳定的固定钟点定义，跨日后重新以当天 `00:00` 为基准。

示例：

- 10 分钟：每小时的 `:00、:10、:20、:30、:40、:50`；
- 30 分钟：每小时的 `:00、:30`；
- 60 分钟：每个整点；
- 120 分钟：每天中国时间的双数小时整点，如 `00:00、02:00、04:00`。

如果当前时间恰好位于对齐点，计算结果必须是下一个对齐点，不能立即重复执行。

保存设置不会立即触发扫描。保存成功后，设置服务通知正在等待的调度器重新读取配置并重新计算下一个对齐时刻，避免调度器继续按旧间隔休眠。重新计算后仍从严格晚于当前时间的下一个对齐点开始。

应用启动后，调度器读取数据库配置并等待下一个对齐点。每轮扫描开始前再次读取一份配置快照，将同一份 `min_market_cap` 和 `min_avg_volume` 同时用于 US/HK：

```text
读取配置快照
  -> 判断 US/HK 交易日
  -> 各市场使用相同阈值执行 Screener
  -> 复用现有指标计算和消息发送
```

配置在一轮扫描期间发生变化时，不影响已经开始的轮次；下一轮采用新配置。

现有并发保护继续保留：上一轮仍在运行时，新轮次跳过并记录日志。

## 缓存与筛选条件

消息推送缓存的日 K 数据不依赖最低市值和最低月均成交量的具体数值。配置降低阈值后，下一轮 Screener 可能返回新股票；现有按需补查逻辑负责为新股票加载日 K。

FastAPI 启动预热和每轮扫描都应读取数据库中的后台配置，不再使用代码中固定的 2000 亿和 1000 万作为运行时筛选条件。默认值只用于首次创建配置记录。

## 错误处理

- 配置读取失败：设置页显示错误和重试入口，不展示伪造默认值；
- 配置保存校验失败：返回统一错误响应，页面保留草稿；
- 配置保存数据库失败：回滚事务，页面保留草稿；
- 调度器读取配置失败：不使用猜测值执行扫描，记录错误并进入可恢复等待；
- 配置变更通知丢失：每轮扫描前再次读取配置，确保最迟下一轮使用数据库最新值；
- 后台配置错误或数据库异常不得导致 FastAPI 退出；
- 日志不得包含 PushPlus Token、长桥密钥或其他敏感信息。

## 测试范围

后端自动化测试覆盖：

- 首次读取时创建并返回默认配置；
- 配置在新数据库会话和应用重启后仍保留；
- GET 返回数据库最新配置；
- PUT 保存完整配置并返回最终落库值和更新时间；
- 间隔的最小值、最大值、步长及非法值；
- 市值的最小值、最大值、步长及非法值；
- 月均成交量的最小值、最大值、步长及非法值；
- 10、30、60、120 分钟的中国时间固定钟点计算；
- 当前时间恰好位于对齐点时选择下一个对齐点；
- 保存后唤醒等待中的调度器并重新计算；
- 保存不立即触发扫描；
- 每轮 US/HK 使用同一配置快照；
- 筛选服务收到数据库中的市值和成交量阈值；
- 配置读取失败时不执行猜测条件扫描；
- 既有并发轮次跳过行为继续有效。

前端验证覆盖：

- 第一次及每次重新进入设置页都调用 GET；
- GET 成功后正确还原三个配置项；
- GET 失败时不展示默认配置，并可重试；
- 草稿未变化时保存按钮禁用；
- 修改草稿后保存按钮启用；
- PUT 请求提交完整配置；
- 保存成功后使用响应值更新页面状态；
- 保存失败时保留草稿；
- 未保存离开后再次进入时以数据库值还原；
- 设置频道不触发股票筛选请求；
- 首页与设置页规格一致但状态互不联动。

全量后端测试和前端生产构建必须继续通过。
